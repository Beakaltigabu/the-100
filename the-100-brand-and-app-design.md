# THE 100 — Brand & Community System

## 1. Brand Overview

### Brand Name

**THE 100**

### Core Concept

**100 days. Your goal. Your commitment.**

THE 100 is a 100-day personal challenge framework where every participant chooses a meaningful physical-activity goal and commits to completing it within 100 days.

The founder's personal challenge is:

**1,000 KM / 100 DAYS**

The community is **not** a 1,000 km challenge.

The community proposition is:

> **Choose your goal. Commit for 100 days. Finish what you started.**

The challenge is designed to transform individual discipline into a shared movement.

---

## 2. Brand Purpose

THE 100 exists to make long-term physical consistency feel:

- simple
- measurable
- social
- achievable
- meaningful

The objective is not to create the world's best athletes.

The objective is to create people who can say:

> **"I committed to something for 100 days, and I finished it."**

---

## 3. Brand Promise

THE 100 gives people:

**A goal.**  
Something concrete to work toward.

**A clock.**  
100 days creates urgency.

**A system.**  
Progress is visible.

**A community.**  
Nobody has to do it alone.

**A finish line.**  
Day 100 means something.

---

## 4. Core Psychological Idea

THE 100 should never communicate:

> "Can you keep up with me?"

Instead:

> **"What are you capable of committing to?"**

Everyone starts from a different baseline.

A beginner completing 50 km and an experienced runner completing 1,000 km are both successful if they honor their commitment.

The competition is primarily:

**You vs. the person you were 100 days ago.**

---

## 5. Founder Story

The founder's 1,000 km challenge acts as the central narrative.

### Founder Challenge

**1,000 KM**

**100 DAYS**

**10 KM/DAY AVERAGE**

This creates the high-stakes story that attracts attention.

But the audience is invited into a much broader idea:

> **"I'm doing 1,000 km. You don't have to. Pick your own number."**

This distinction is essential.

The founder's challenge is the **story engine**.

THE 100 is the **community engine**.

---

## 6. Positioning

THE 100 sits between:

- fitness challenge
- accountability system
- social movement
- personal development
- endurance challenge
- community

It should NOT feel like:

- a fitness app
- a running club
- a race organizer
- a Strava clone
- a bodybuilding program
- a corporate wellness platform

It is:

> **A commitment movement built around 100 days.**

Build a lightweight web application that allows people to:

1. Discover the challenge
2. Register
3. Establish a baseline
4. Choose a 100-day goal
5. Commit
6. Join the private Telegram community
7. Connect Strava
8. Track personal progress
9. View milestones

The product must be:

- mobile-first
- fast
- simple
- responsive
- installable as a PWA
- easy to maintain
- designed for gradual scaling

## Telegram Linking Architecture

Do not use Telegram username as the primary identity.

Generate a cryptographically random, one-time token.

Conceptual flow:

```text
THE 100 account
      ↓
Generate one-time token
      ↓
Open Telegram bot deep link
      ↓
Bot receives token
      ↓
Server validates token
      ↓
Associate Telegram user ID
      ↓
Generate/use private group invite
      ↓
Member joins community
      ↓
Mark telegram_connected = true
```

Token requirements:

- cryptographically random
- single-use
- short-lived
- no personal information
- no password or credential data

# 15. Strava OAuth

Use OAuth 2.0.

Request the minimum permissions required.

For reading activities, request the appropriate read scope.

Do not request write permissions unless a future feature genuinely requires them.

Never expose Strava credentials or tokens to frontend JavaScript.

---

# 16. Strava Webhook Architecture

Do not continuously poll Strava.

Use webhooks:

```text
Strava
   ↓
Webhook
   ↓
Webhook endpoint
   ↓
Validate event
   ↓
Queue event
   ↓
Process asynchronously
   ↓
Fetch/update user's activity
   ↓
Update personal dashboard
```

Webhook handlers must acknowledge quickly.

Heavy work belongs in an asynchronous queue.

Handle:

- activity create
- activity update
- activity delete
- athlete deauthorization

---

# 17. Strava Data Privacy

A participant may see their own Strava-derived activity.

A participant must not see another participant's Strava-derived activity.

Do not build V1 features such as:

- public Strava activity feed
- Strava-powered public leaderboard
- member-vs-member Strava statistics
- aggregate Strava distance
- AI analysis of Strava data
- community analytics based on Strava data

Treat Strava API policy as a hard architectural constraint.

# 33. Security Requirements

Never expose:

- Strava client secret
- Strava refresh tokens
- Telegram bot token
- session secrets
- database credentials

Secrets remain server-side.

Encrypt sensitive integration tokens at rest.

Use HTTPS.

Use secure HTTP-only cookies or an equivalent secure authentication mechanism.

Rate-limit:

- authentication
- activity logging
- Telegram linking
- OAuth callbacks

---

# 34. Strava Token Handling

Store, securely:

```text
strava_athlete_id
encrypted_refresh_token
encrypted_access_token
expires_at
scope
connected_at
```

Refresh access tokens when required.

Never expose tokens to the frontend.

When Strava issues a replacement refresh token, replace the previous stored refresh token.

---

# 35. Strava Disconnect

When the user disconnects:

1. Revoke authorization using the current Strava-supported mechanism.
2. Remove stored Strava credentials.
3. Remove permitted cached Strava-derived data.
4. Mark connection disconnected.
5. Confirm to the user.

When authorization is revoked, handle the deauthorization webhook and applicable data deletion requirements.
